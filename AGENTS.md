## Cardenal
Aplicar primero .cardenal/templates/execution-policy.md; en Codex tambien .cardenal/templates/codex.md.
Para relevar el repositorio usar .cardenal/templates/inicializate.md (/inicializate); para trabajar una feature usar .cardenal/templates/feature.md (/feature). /feature orquesta relevamiento, roles, verificación y cierre; spec, plan, tareas e implementación se ejecutan con /sdd:* (fuente: .cardenal/sdd/<etapa>.md) en specs/<NNNN-slug>/. Roles: analyst = analyst, front = front, back = back, testing = testing. Inicializate no exige una feature. Trabajar en la rama y checkout actuales; no crear ramas, worktrees o PR ni cambiar ramas o hacer merge salvo pedido explícito. Cargar solo el prompt de la etapa activa en .cardenal/prompts y las fuentes pertinentes; no releer todas las guías. Preguntar dudas que alteren comportamiento o selección de roles antes del trabajo dependiente; usar QA manual por defecto; automatizado solo por pedido explicito. No inventar decisiones, pruebas, agentes ni revisiones. Al iniciar una conversación leer docs/public/README.md y docs/tech/README.md si existen, luego solo fichas y dependencies pertinentes. Respetar .cardenal/constitution.md. Documentar cada feature implementada en ambas audiencias, no solo en specs/. Los JSON de control viven en .cardenal; la documentación Markdown vive en docs/public y docs/tech; docs/private queda local e ignorado por Git para información confidencial; user-memory es local e ignorado por Git. No copiar secretos ni transcripciones. Validar estructura y comportamiento por separado. Solo contadores del proveedor acreditan consumo de tokens.
